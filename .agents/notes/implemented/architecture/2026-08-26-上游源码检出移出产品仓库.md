# 上游源码检出移出产品仓库

## 背景

M1 最初把 DeepSeek Harness 固定为产品仓库内的 Git submodule，同时让实际
运行和交付使用 npm 包。源码 checkout 只承担审计与升级对照，却因此进入
每个派生产品的仓库拓扑；复制基座会携带一个不参与运行的目录，混淆产品
依赖和开发者参考资料。此决策修订
[`首个上游 pin 与补丁清单`](../process/2026-08-25-首个上游-pin-与补丁清单.md)
中的仓内 submodule 方案，不改变 npm 运行闭包。

## 决策

- 从 Convax Next 删除 `.gitmodules`、gitlink 和仓内
  `deepseek-harness/`。
- `upstream.json` 继续记录官方仓库、完整 source commit 与精确 npm 版本，
  并声明可选审计 checkout 的默认位置为同级 `../deepseek-harness`。
- 普通 install、check、开发、smoke 和打包只依赖 npm 闭包，不要求本机
  存在源码 checkout。
- `yarn upstream:*` 是显式审计命令；执行前校验同级 checkout 存在且 HEAD
  与 manifest 完全一致。
- 布局门禁明确拒绝产品仓库根出现 `.gitmodules` 或
  `deepseek-harness/`，防止派生项目重新携带上游源码。

## 被否方案

- **继续使用 submodule**：版本可审计，但把只读参考强加给每个产品 clone，
  仓库职责错误。
- **在产品仓库放未跟踪目录或 symlink**：复制、IDE 索引和本地脚本仍会看到
  该路径，也容易被误当成运行依赖。
- **彻底丢弃 source commit**：npm 版本可运行，但升级时失去与源码变更的
  精确映射。

## 可证伪的验收证据

- Git tree 不含 `.gitmodules` 或 `deepseek-harness` gitlink。
- `yarn check:layout` 在没有 sibling checkout 时通过，并会拒绝仓内同名
  目录。
- 同级 `../deepseek-harness` 固定到 `b150a551…` 时，`yarn upstream:version`
  可执行；切换到其他 commit 时命令必须失败。
- `yarn check`、`yarn smoke:upstream` 与 `yarn package:dir` 不从 sibling
  checkout 解析任何运行依赖。

## 遗留风险

同级 checkout 是多个产品共享的开发者便利，一次只能处于一个 commit。
不同产品需要不同上游版本时，执行审计命令前必须切换到各自
`upstream.json` 指定的 commit；这不影响任何产品运行或打包。
